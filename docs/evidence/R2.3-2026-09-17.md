# R2.3 — a real student directory, and where each value came from

Run on 2026-09-17 on branch `r2-3-directory`. Baseline `6fde807` (R2.1/R2.2).
Verified against a production build on `localhost:3100` with the R0.2 fixtures.

## 1. `/students` — finding a child without knowing their class

PLAN §3a: "Add a real searchable directory instead of forcing access through
attendance." Until now the only route to a student's record was the register of
whichever class they happened to be in — which works if you already know the
class, and is the whole problem if you do not (S-10).

A plain **GET form**, with every filter in the URL. No client state, so Back
works, a bookmark works, and a link pasted into WhatsApp opens the same list for
whoever receives it. It also means the screen ships no JavaScript of its own.

Guarded on a new `students:view`, held by **admin and office only**: PLAN §3
puts Students on those two navigations and nowhere else, and a teacher already
has her own classes on `/teach`.

`/students` is now **second on the office bar** — `मुख्य · विद्यार्थी ·
जानकारी · ऐप · और` — which is PLAN §3's office row exactly, for the first time.

### Filtered and counted in Postgres

The staff list is a few dozen and ships whole (D-29). The roster is a few
hundred and will be a few thousand, and PostgREST truncates a read at a
thousand rows **with no error** (D-62) — so a directory that fetched everything
would work today and start silently hiding children the year the school grew.
Scope, search, count and page all happen in the database; 50 rows a page.

Scope comes from **VPPS One's own enrolments**, not `public.students.class_id`:
that column holds where a child is today and the fee app overwrites it on
promotion, so filtering on it would put last year's Class 6 into this year's.

## 2. The search bug the browser found

Three kinds of thing get typed into a school's search box, and `queryKind()`
tells them apart: a bare number is an **exact** admission number (typing "12"
must not return every child whose SR contains a 12), ten digits is a **phone**,
and anything else is a **label**.

The first version searched labels against names only. Exercised in the browser:

| Query | Before | After |
|---|---|---|
| `Aarti` (name) | 1 | 1 |
| `Rajesh` (father's name) | 9 | 9 |
| `002` (bare number, exact) | 0 | 0 |
| **`TEST-CL6-002` (this school's SR)** | **0** | **1** |

**This school issues alphanumeric SR numbers.** They never reach the
exact-match branch, so pasting one from a spreadsheet searched only names and
found nothing — which reads as "that child is not here". The loose branch
searches `admission_no` as well now. Covered by `tests/directory.test.ts`,
including a case that reads the repo's query back so the rule cannot be
dropped.

## 3. Source labels — S-10

`vppsone.student_records` holds what VPPS One has accepted about a child, with
a `source`. Until now the card rendered the value and not where it came from:
an approved human correction and an imported figure look identical once they
are both text on a card, and which one it is decides whether somebody rings the
parent to check.

Each value now carries a badge — **A teacher** / **The office** / **An import**
— with the section saying "each value says where it came from". A source the
app has never heard of renders as itself rather than being forced into one of
the three: saying "an import" about something that was not one is worse than
saying a word nobody recognises.

Verified in the browser: guardian phone `9000000001` with an **अध्यापक**
(a teacher) badge.

## 4. The fee link, finally rendered

R1.1 built the context-link builder and nothing called it. The student page now
does, and it behaves as designed:

```
https://vpps-one.vercel.app/protected/students?query=TEST-CL6-002
```

A **search** link carrying the SR number — not a deep link carrying a dev UUID
that means nothing in the fee app's live database (D-122). The button says
**"इस बच्चे को खोजें"** (Find this child), not "Open this child", and the line
above it explains why. Shown only to roles with `collection:view`, alongside the
fee standing that was already there.

## 6. Limitations

- **The detail screen is still at `/teach/student/[id]`.** One student record,
  not two — but the URL reads oddly from a directory, and its guard is
  `attendance:view` rather than `students:view`. Moving it to `/students/[id]`
  with an alias is R4.1's, where the student workspace is rebuilt; splitting it
  now would mean two detail screens drifting apart.
- **No fee-app deep link is possible at all today**, so the `detail` branch of
  the builder has never run against a real destination. It is unit-tested, and
  it stays unexercised until a fee test origin exists (B-16).
- **Search is not diacritic- or transliteration-aware.** "Meera" does not find
  "मीरा". Both spellings exist in this school's data, and matching across them
  needs either a stored transliteration or a Postgres extension — a real piece
  of work, not a tweak. Recorded rather than half-done.
- No sort control, no export, no bulk selection. The plan puts those with the
  import/export work in R4.
- Photos are not shown: the roster has no photograph column VPPS One can read,
  and photo capture is R4.2.
- No browser journey asserts a search end to end. The phone baseline opens the
  directory and a search URL and checks layout; the matching itself is verified
  by the four-case browser probe above and by unit tests.
