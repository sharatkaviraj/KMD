# R1.2 — one Home per role, a bar that leads with the role's work, a grouped sidebar

Run on 2026-09-17 on branch `r1-2-role-navigation`. Verified against a
production build on `localhost:3100` with the R0.2 fixtures.

## 1. B-22 — the viewer's reach, closed

`view_only` held `attendance:view`, and six screens are guarded on it: the
teacher workspace, the register form, a class's roster, the corrections queue,
the monthly register and a child's card. Every one is either an editable form
or a list of named children, and PLAN §3 gives the viewer "read-only
information; **no editable forms or per-child actions**". It also put a Teach
tab on a viewer's bar leading to an empty teacher workspace.

The permission is removed. The attendance *figures* PLAN §3 does promise the
role — "school summary, attendance completion" — are a count on its own Home,
read server-side under `dashboard:view`; a permission is about screens, not
rows, so R2.2 does not need it back.

Verified in the browser: a view-only account's navigation is exactly
`/dashboard` and `/timetable`, and `/teach/attendance` answers the
access-denied screen naming `attendance:view`.

**`npm run smoke:roles` now runs with `--strict`**, and passes:

```
222 of 222 executed · 222 as expected · 0 known drift · 0 failed
```

All three readings — the permission map, each page's own guard, and PLAN §3
written out by hand — agree for the first time.

## 2. One Home per role

`homeFor(role)` — `/teach` for a teacher, `/dashboard` for everyone else.
Applied at every landing: `/`, the login page's already-signed-in redirect, the
login action's fallback, `/auth/confirm`, the school-name link in the header,
and the "Go home" button on access-denied.

The fallback is resolved **after** the profile is known, so
`admitSignedInUser()` now returns the role rather than the caller reading it a
second time. A deep link still wins; the role's Home is only what happens when
nothing was asked for.

Verified: signing in as the QA teacher with no `next` lands directly on
**"मेरा दिन"** with "Class 1 · हाज़िरी लें" as the first thing on the screen.
Before this she landed on a card showing her own email address and had to tap
again — the whole of B-03, and two taps where PLAN §1 asks for one.

`npm run dev:login` no longer defaults `next` to `/dashboard`, so it exercises
the same path.

## 3. B-04 — the bar leads with the role's own work

One shared order used to give every role Home, Teach, Cover, Timetable, Exams —
so the office reached SamPark through More, behind three screens it does not
use, and `/apps` (R1.1) never appeared on its bar at all.

`NAV_PRIORITY` is an ordered list per role, following PLAN §3's navigation
column. Where a screen it names does not exist yet (Students is R2.3, a
teacher's Requests inbox is R3.3) the row is simply shorter; nothing is
invented to fill a gap, and anything unlisted still falls to More.

## 4. The grouped desktop sidebar

PLAN §3: "Desktop gets grouped sidebar navigation … rather than the phone's
first-four-items-plus-More limit." A 1440px window has room for everything a
role may open, and hiding four screens behind a hub built for a thumb is the
phone's constraint following somebody to their desk.

`sidebarFor(role)` returns three groups in the order a day runs. There is no
More on it — nothing is hidden, so a hub listing what did not fit would be an
empty page. An empty group is dropped rather than rendered as a heading with
nothing under it, and each group is a landmark with its heading as its
accessible name.

Verified at 1440×900 as the office:

| Group | Screens |
|---|---|
| आज का काम (Today's work) | Home, SamPark, Teach, Cover |
| रिकॉर्ड (Records) | Apps, Timetable, Exams |
| व्यवस्था (Setup) | Academics, Staff |

Nine screens, all of them, against the four-plus-More the phone shows.

## 6. Limitations

- **The homes themselves are still thin.** `/dashboard` is a profile card plus
  links for five roles; the queues with owners and counts are R2.2, and the
  teacher's real priorities are R2.1. This task decided *where* each role
  starts, not what they find there.
- PLAN §3's teacher bar names "My classes" and "Requests", and the office bar
  names "Students". None of those routes exists yet (R2.3, R3.3), so those bars
  are shorter than the plan's final shape.
- No aliasing work was needed: no route moved, so no bookmark broke. `/dashboard`
  is still openable by a teacher; it is simply not where she lands.
- The desktop sidebar was checked at 1440×900 only. 768×1024 and the full
  responsive sweep are R7.2.
- B-23 (unnamed `<section>` landmarks) is untouched. The new sidebar groups do
  carry `aria-labelledby`; the `Section` primitive still does not.
