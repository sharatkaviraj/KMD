Run on 2026-09-17 on branch `r2-1-teacher-today` (R2.1 and R2.2 ship together;
R2.2's commit is separate). Verified against a production build on
`localhost:3100` with the R0.2 fixtures.

## 1. What `/dashboard` was

A profile card and a list of links, identical for all six roles, for every
phase since 1.2 (B-03). It told a staff member what they were and where they
could go, and nothing about what needed doing.

## 2. Exceptions with counts and owners

PLAN §3 asks the admin home for "exceptions with counts and owners" and the
office home for "actionable queues with owners". The **owner** is the
load-bearing half: a number with no name beside it is somebody else's problem
to everybody who reads it, and the register that has not come in belongs to a
teacher rather than to whoever happens to have the dashboard open.

`src/modules/home/domain/attention.ts` is pure — it takes counts somebody else
read and decides what each role sees, in the order that role works.

| Role | Queue, in order |
|---|---|
| admin | registers · staff away · changes to review · corrections · failed jobs |
| office | changes to review · corrections · registers · staff away |
| academic coordinator | staff away · registers |
| exam coordinator | — |
| teacher | — |
| view only | — |

The empty rows are deliberate:

- **Exam coordinator**: PLAN §3 wants incomplete papers and report readiness.
  Neither has a cheap count yet, and an empty queue is honest where a wrong one
  is not. R5.3 owns it.
- **Teacher**: her home is `/teach`, and her exceptions — her register, her
  cover — are already the top of it. A second list of the school's would be
  somebody else's work on her phone.
- **View only**: figures, not tasks. PLAN §3 gives that role "read-only
  information; no editable forms or per-child actions".

## 3. Unavailable is not zero

D-93 is the whole reason this file is careful: the daily summary job once
reported "19 classes have no class teacher" because `const { data } = await …`
swallowed a query error. On a dashboard that mistake is worse — an
administrator reading a confident **0** concludes the school has nothing
outstanding.

So each read is attempted individually, a failure records its key, the count
comes back **null**, and the row renders a dash with "this count could not be
read just now" where the owner line would be. `needsAttention()` treats a null
as needing attention, because nobody knows that it does not.

`homeSummary()` also fetches only the counts the role will display: a viewer
does not need the collection queue, and a dashboard reading six tables to
render two numbers is what R7.1 comes back to delete.

## 4. A density fix found by looking

The owner line first rendered with `flat()`, which gives a bilingual reader
both halves: "किसका काम · Whose: शैक्षणिक संयोजक · Academic coordinator" is
wider than a 360px phone and truncated to "शैक्षणिक संयोजक · A…". It uses
`primary()` now — one language on that line, whichever the reader asked for.

## 6. Limitations

- **No fee summary on the admin home.** PLAN §3 wants one, through the
  authoritative read model. A school-wide fee figure is a new read against the
  fee app's schema and belongs with R6, where the reconciliation rules
  (principal ≠ late fee, write-off ≠ collection) are being settled. Rendering
  an unreconciled number now would be exactly the "₹0 where it should say
  unavailable" the design package warns about.
- **No student search box.** PLAN §3 puts one on the office home; the directory
  it would search is R2.3. A search field posting to a route that does not
  exist is a dead control.
- **No uncovered-period count.** "Staff away today" is a real count from
  `teacher_absences`; how many of their periods are still uncovered needs the
  planner's own context, which is a heavier read. The card sends the
  coordinator to `/substitutions`, where the real figure is.
- The queue's destinations are screen-level, not filtered. PLAN §2's "cards
  drill into the matching filter/scope" is only half met: `/collection/review`
  and `/jobs` land on the right thing, but "19 registers not in" lands on the
  attendance screen's class picker rather than on a filtered list of the
  nineteen. There is no such list yet.
- Nothing here has a browser journey. The counts are verified by screenshot and
  by unit tests over the pure layer; no test presses a queue row and checks
  where it lands.
