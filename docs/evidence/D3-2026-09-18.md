# D3 — the design language on every screen

18 September 2026. Branch `d3-design-language`, from `main` at `0494e67`
(D1/D2, PR #29, deployed and verified live). Read `D0-2026-09-17.md` for what
belongs to this repository and what does not; this file records the pass that
took the Ledger Calm 2 language from three role homes to the whole app.

## The finding that shaped it

Opening the atlas's `students`, `staff`, `attendance`, `review`, `cover`,
`setup` and `reports` side by side, they are **one composition**: a white card
whose head carries a title and a line of context, and whose body is a list of
rows separated by hairlines rather than by gaps.

The role homes had that by hand. Every other screen had a bare
`<ul className="space-y-2">` of separately-bordered cards — a different density
that reads as a different product. So the pass is mostly one component, applied.

## What was added

| Piece | What it is |
|---|---|
| `Panel` | Card + header (title, context line, action) + hairline-divided rows + optional footer |
| `PanelRow` | One row: icon tile or lead value, title, detail, trailing badge, optional href. 64 px, whole row is the target |
| `FootNote` | The quiet card under the content that explains one rule — "A reliable search", "Role and assignment are separate" |
| `RowAction` | The small "Open →" link that ends a row |
| `StateCard` | The atlas's full-page state: symbol, sentence, **and a way on** |
| `PageHeader` `eyebrow` | Already added in D1; applied everywhere in this pass |

## What was deliberately left as cards

`/collection/review`, `/substitutions`, `/collection/rounds/[id]`,
`/collection/messages`, `/jobs`, `/teach/corrections`,
`/substitutions/policies` and the detail and form screens keep `Card` +
`Section` + `Field`.

That is not an omission: the atlas draws them the same way. A review row is a
before/after diff with a decision form in it, a cover row carries its candidate
list, a job row carries its run history. `PanelRow` is for a row that fits on a
row, and forcing these into one would have deleted the content that makes them
worth opening. They were already built from the shared kit, and they now carry
the eyebrow with everybody else.

## A defect the suite caught immediately

**B-42 — the first `Panel` turned every list into a stack of `<div>`s.** It
rendered its rows inside a plain `<div className="divide-y">`, which is what
the markup looked like it needed. `teacher-attendance.spec.ts` counts
`getByRole("listitem")` and found **0 of an expected 15**.

The test was right and the component was wrong. Every panel in this app holds a
list of like things — children, staff, classes, exams, requests — and a screen
reader that cannot announce "list, 15 items" is reading fifteen unrelated
paragraphs. `Panel` is a `<ul>` now and `PanelRow` is an `<li>`, with the link
*inside* the item rather than being it: a list whose items are themselves
anchors is announced as a list of links rather than of things.

Worth recording because of how it was nearly missed. The first re-run after the
fix still failed — against a preview server holding the previous build, because
Playwright's `reuseExistingServer` had attached to one this session had already
started. The failure looked identical to the real one. Rebuild **and** restart
the server before believing a workflow result.

## B-43 — the supporting column could remount the work beside it

The register's aside is conditional: the "mark the exceptions first" card is
there while the register is open and gone once it locks. `HomeColumns` returned
a bare fragment when there was no aside and a grid when there was — **two
different element types at `main`'s position**.

So the moment a teacher pressed Save, the register locked, the wrapper changed
shape, and React unmounted and remounted everything under it. `RegisterForm`'s
client state went with it, including `saved` — so the "Saved" acknowledgement
she had just earned never appeared. The data was safe (the queue is in storage
and the row was written), but the screen stopped telling her so, which on this
particular screen is most of the point.

Caught by `teacher-attendance.spec.ts` asserting that the register reports
itself submitted. The wrapper is now the same `div` whether or not there is an
aside; only the column track and the second child are conditional.

**This one is worth remembering as a shape of bug**, not just a fix: any layout
component that returns a different tree depending on a prop will remount its
children when that prop flips, and the damage shows up in whatever client state
was underneath.

## Deviations, added to the D0 list

6. **The live register summary stays inside the register form.** The atlas puts
   Present/Absent/Late/Excused in the supporting column. Those counts are
   client state that the offline queue owns; lifting them out means threading
   that queue's state through the page, and the queue is the part of this
   screen least worth destabilising for a layout. The counts stay in the
   form's sticky bar, where they already were and where a phone can see them;
   the column carries the guidance card instead.

## What was run

| Check | Result |
|---|---|
| `npm run check` | typecheck, lint, tests, production build — green |
| `npm run smoke:workflows` | **42 of 42 passed, 9.3 min** |
| Browser pass, production build, 1440 px | `/dashboard` (admin), `/students`, `/teach/attendance` with and without a class chosen |
| Browser pass, 360 px | `/teach/attendance`: status controls stacked under the name, no horizontal overflow, no control under 44 px |

Three runs of the suite were needed to get there, and the two failures on the
way were both real: B-42 and B-43 below. `collection-freeze.spec.ts` failed on
two of those runs and passed on the third at 36.0 s — it is the same
warmth-dependent timing as B-40, not an interaction with this change.

**On the timings.** A cold `next start` answers the first `/teach` in **28
seconds**; warm requests are 0.3–4.6 s. That alone can exhaust a 60-second
test budget, and it is why a spec that passes in a warm suite can fail when run
by itself against a freshly started server. Anything read from a single
workflow run should be treated with that in mind.

The responsive baseline in `tests/e2e/responsive-baseline.spec.ts` covers
`/teach`, `/teach/attendance`, `/dashboard`, `/apps`, `/collection`,
`/students`, `/collection/rounds`, `/collection/rounds/new` and `/preferences`
at 360, 390 and 430 px — which is most of what this pass touched — asserting no
page-level horizontal scroll and no control under 44 px tall.

## Evidence gaps

- **Not every screen was opened by eye.** The eyebrow pass was mechanical
  across 37 files and is covered by the build and by the responsive suite, but
  the detail and form screens were read rather than looked at.
- **Not a physical-device pass.** Emulated widths in Chromium, as before.
- The fee screens (`accountant`, `payments`, `dues`, `receipts`, `fee-report`)
  remain the `veerpatta/schoolfees` repository's, exactly as D0 recorded.
