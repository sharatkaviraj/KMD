## 3. The bug the fixture found immediately — B-21, fixed

With a teacher who has periods, `/teach` renders the period badge. It printed
`timetable_slots.period` raw, and that column is **0-based** (0–7 for an
eight-period day). A teacher's first lesson read **“0”** and her last read
**“7”**.

Six other render sites each did `period + 1` by hand; this one forgot. It had
been shipping since Phase 3.1 and nothing could see it, because no teacher
account had a period to render.

Fix: `src/modules/timetable/domain/periods.ts` — `periodNumber()`,
`periodIndex()`, `isPeriodIndex()` — used at all seven sites.
`tests/periods.test.ts` asserts the arithmetic and then scans every `.tsx` for
the two shapes that caused it: a hand-written `period + 1`, and a raw
`{…period}` rendered as JSX children (prop passing and template literals are
excluded, because passing the index around is what it is for).

Verified against the broken state before being trusted (D-96): restoring
`{slot.period}` fails the file's own case and nothing else.

Browser evidence, production build at 375×812:

- teacher 1, Hindi: “करना बाकी → Class 1 · हाज़िरी लें”, periods **1, 2, 3, 3, 3…**
- teacher 2, English: “Needs doing → Class 7 · Take the register”, periods
  **1, 2, 3, 4, 5, 5…**, classes 7/8/9/11 Science/11 Commerce — no overlap with
  teacher 1's Classes 1–5.

## 4. New defect raised — B-20

The Today card lists **20 rows for an eight-period day**. A parallel subject
(ELGA, taught to Classes 1–5 at once) is one slot per class in the timetable
model, so period 3 renders as five separate rows reading Class 1, Class 2,
Class 3, Class 4, Class 5. The teacher is in one room.

Not fixed here: the right rendering is a product decision about how a combined
period reads, and that belongs to R2.1's Teacher Today work. Recorded with its
reproduction rather than patched in passing.

## 5. The mock messaging provider

`dispatch()` now goes through a typed adapter (PLAN §2).
`src/modules/collection/data/message-provider.ts` chooses from
`MESSAGE_PROVIDER`:

- unset or `aisensy` — unchanged behaviour, still refuses without an
  `AISENSY_API_KEY` this repository does not carry (rule 8).
- `mock` — decides from the destination's last digit, touches no network, and
  is **refused outright on a live deployment**.

| Last digit | Outcome |
|---|---|
| 0–4 | sent |
| 5 | slow (1.2 s, then sent) |
| 6 | timeout |
| 7 | rate limited (the 429 case) |
| 8 | server error (the 500 case) |
| 9 | duplicate — succeeds with a **stable** id derived from the send |

The `duplicate` case is what makes a repeated delivery callback testable: the
provider id is identical on every attempt, so a second dispatch is
indistinguishable from a replay of the first, and `recordDispatch()`'s
`.neq("status", "sent")` is what has to stop a second `sent_at`.

Every mocked id is prefixed `mock:` and that prefix lands in
`message_sends.provider_message_id`, so a row that was never really sent can
never be read as one — by a screen, by a later query, or by somebody reading
the table at cutover.

`mayDispatch()` is unchanged and still runs first: a parent-facing row is
refused whichever provider is configured (D-10).

## 7. Limitations

- The role smoke is still guard-derived (B-09) and still tolerates a missing
  fixture (B-10). Both are R0.3.
- Nothing here exercises a mutation through the browser. Saving a register,
  marks or a request remains untested end to end; R0.3 owns the first two
  journeys.
- The mock provider's *adapter* is unit-tested through its domain decisions
  only. No screen has been driven through a 429 yet — that needs the message
  queue screen and a seeded recipient, which is R3.4.
- `--edge-classes` is not left applied. It changes what the register screens
  show, so it is opt-in per run.
