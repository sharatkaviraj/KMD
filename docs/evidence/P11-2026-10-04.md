# P11 — Archive catalogue and restore drill

Branch `p10-sampark-import-photos`, on main `f3bb72e`. Target: schoolfees-dev
(`wtgxcptmucjerhufzjcf`) only. Procedure: `docs/ARCHIVE.md`. Decision: D-238.

## What changed

- **`/archives`** (administrator, `jobs:run`) builds an archive of every
  `vppsone` table and every document and photograph into the private
  `vppsone-archives` bucket, with a `manifest.json`. The manifest holds:
  - per table: row count, Postgres md5 of the canonical rows and sha256 of the
    file;
  - per object: sha256 and size;
  - the schema version, the app commit and the totals.

  The catalogue row (`vppsone.archives`) is written first, so a failed build is
  recorded with its reason. Nothing is deleted to make an archive, and the fee
  app's `public` tables are not in it.
- **Rows travel as text.** `archive_table_export` returns the rows as the text
  Postgres wrote, with their count and md5 from the same statement and so the
  same snapshot. The app writes that text to the file without parsing it, so
  `0.50` cannot come back as `0.5`.
- **The restore drill** (`restore_drill_table`, run from the screen or by the
  verifier):
  - reloads each file into a scratch table of the same shape, in a transaction
    that leaves nothing behind, and must reproduce the archived row count and
    md5;
  - re-hashes every object;
  - round-trips one object through a scratch prefix;
  - checks that the stored manifest agrees with the catalogue's.

  Every drill is kept in `vppsone.restore_drills`.
- **One engine** (`src/modules/archives/data/archive-engine.ts`) takes a
  client as an argument, so the screen and `verify:archive` run the same code.

## Executed evidence

| Check | Result |
|---|---|
| `npm run verify:archive` | **10/10**. Every table is in (66 tables, about 4,500 rows) and every document and photograph is copied (5 files, one planted synthetic photograph). A quiet table's archived digest equals the live digest. The drill, run with the catalogue's jsonb copy of the manifest, reloads all 66 tables to the same digest, re-hashes every file and round-trips one. Four kinds of tampering each fail the drill: a file checksum, a reload digest, a missing file, a photograph's bytes. The bucket is private. Everything is removed afterwards |
| In-database round trip | every one of the 66 tables reloads to an identical md5 (`archive_table_export` → `restore_drill_table`) |
| `tests/e2e/archive-drill.spec.ts`, production build | passed. An administrator builds an archive (66 tables, ready in about 15 s on dev) and runs a drill, which passes with 66 tables checked |
| `tests/archive-engine.test.ts` | 2: manifest comparison ignores key order at every depth, and still sees a changed value or a reordered array |

**Found by the browser journey, not the verifier.** The drill compared the
manifest beside the files with the catalogue's copy as written JSON. The
catalogue keeps it as `jsonb`, which reorders keys, so on the screen every
drill failed with "manifest". The verifier had drilled with the in-memory
manifest and could not see it. The comparison is now canonical, the verifier
drills with the catalogue's copy, and a unit test pins the comparison.

## Not established

- **An off-site copy.** Archives live in the project they copy. The manual
  Drive fallback is written down; automating it needs the school's
  authorization.
- **A restore into a fresh project.** The drill proves each table reloads into
  its own shape and each byte comes back. Loading a whole archive into an
  empty project, in dependency order, has not been rehearsed end to end.
- **Scheduled archives** (plan job 18, the nightly health and backup check).
  Archives are made by hand.
