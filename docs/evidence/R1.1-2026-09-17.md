Run on 2026-09-17 on branch `r1-1-app-registry`. Baseline `01da4d4` (R0.3).
Verified against a **production build** on `localhost:3100` with the R0.2
fixtures; the deployed app does not carry `/apps` until this merges.

## 1. What B-01 was

There was no way from VPPS One to either sibling application. `navigation.ts`
had no app registry and no screen mentioned School Fees or SamPark at all.

## 2. The registry

`src/platform/config/apps.ts` — PLAN §2's "typed registry with stable IDs,
names, environment, origin, visibility and validated route builders".

| Property | How it is held |
|---|---|
| Origin | read from `app-origins.ts`, never written here |
| Name | `SamPark — Student information`, `School Fees — Payments and dues` (PLAN §3a), as Hindi/English pairs |
| Environment | the **destination's** dataset, not this app's |
| Visibility | `admin` and `office` only |
| Routes | an allow-list; anything not in it cannot be linked to |

Two properties carry the weight:

**Nothing else in `src/` may write a sibling hostname.** `tests/apps.test.ts`
scans every `.tsx`/`.ts` outside the two config files for
`https://…vercel.app` and fails on a match. Two of the three hostnames a reader
would guess are wrong and one belongs to a different company (B-15).

**A link never carries an id across a dataset boundary.** VPPS One is on
schoolfees-dev and both siblings are on live data, so `idsTravelBetween("dev",
"live")` is false and the student builder falls back to the destination's own
search screen:

```
schoolApp("schoolfees").student({ studentId, search: "1042" }, "dev")
  → { kind: "search", href: ".../protected/students?query=1042" }

schoolApp("schoolfees").student({ studentId, search: "1042" }, "live")
  → { kind: "detail", href: ".../protected/students/<uuid>" }
```

SamPark never gets a detail link at all, in either direction: it keeps its own
text student ids, mapping them to fee UUIDs is R3.1's work (S-10), and guessing
by name is what `PARITY.md` forbids outright.

`kind` exists so the caller can label the button honestly — "Find this child"
is a different promise from "Open this child", and shipping the second while
doing the first is how somebody stops trusting a button.

  `vpps-one.vercel.app` for School Fees.

Verified in the browser.

### Office and admin home

Both apps now sit directly under the profile card on `/dashboard`, above the
list of screens, each with its environment label and hostname. PLAN §5 R1 asks
for them on the office/admin home "immediately"; until R2.2 gives that screen
real work, it is the most useful thing on it.

### Navigation

`/apps` is a nav item on `apps:view`. **It does not currently appear on the
office's bottom bar**: office may open ten screens, the bar holds five, and the
shared order puts Teach, Cover and Timetable first — which is B-04 exactly, and
R1.2 owns it. It is on the More hub, and the home shortcut covers the daily
need in the meantime.

## 5. Limitations

- **No fee workflow is verified.** Every link lands on the fee app's own login
  or dashboard; what happens after that is R6, and R6.2 remains blocked on a
  staff-reachable fee test origin (B-16).
- No student context link is rendered anywhere yet. The builder exists and is
  tested; the screen that uses it is the student summary in R2.3.
- Sign-in and return paths across apps were not measured with a stopwatch. The
  card says a separate sign-in may be needed; how often it actually is, is a
  question for the staff walkthrough in R8.3.
- The F-row destinations beyond the two home links are not mapped yet. `apps.ts`
  carries the paths (payments, transactions, defaulters, reminders, requests,
  review) and R6.1 turns them into screens.
- `/apps` is missing from the office bottom bar (B-04, R1.2).
