# R3.4 (part 1) — the queue says when the record moved, and when a newer answer arrived

Run on 2026-09-17 on branch `r3-4-review-precedence`. Baseline `fbcfb4a` (R3.3).
Verified against a production build with the R0.2 fixtures on schoolfees-dev.

**This is part of R3.4, not all of it.** The round-aware review, staleness and
superseding are done and verified; the mock message retry and the S-01–S-09
acceptance pass are not. §6 says exactly what is left.

## 1. Two failures that look like nothing

Both of these render as an ordinary row with a reasonable value in it. Neither
produces an error, and accepting either does something nobody intended.

**Stale (S-07).** A request freezes what the teacher was shown (R3.1), which is
what makes "old → new" mean anything. But the record underneath carries on: the
office corrects a number on Tuesday, the teacher's Monday answer arrives on
Wednesday, and accepting it silently reverts Tuesday's correction.

**Superseded.** Two rounds asking the same class for the same thing is the
ordinary case — the office asks in April, half the answers come back, and it
asks the stragglers again in June. A teacher who answers both leaves two
pending rows for one child and one field, and a queue showing both asks the
office to adjudicate a question it cannot see the shape of.

## 2. What was built

`src/modules/collection/domain/precedence.ts`, pure:

- `stalenessOf({shown, heldNow})` — compared against the **frozen**
  `previous_value`, never a value re-read now. Re-reading is the bug freezing
  exists to remove, and doing it here would make every answer look current.
- `supersededIds(answers)` — the later answer wins; the earlier is **marked**,
  not deleted, because "what did she say in April" is a real question when
  June's answer looks wrong.

Three refusals in `supersededIds` matter more than the rule:

| Case | What it does | Why |
|---|---|---|
| An accepted or rejected row | never superseded | rewriting a decision makes the audit trail a record of what the app thinks, not of what anybody did |
| Two answers with the same timestamp | neither wins | picking one by row order is how a queue starts depending on which way a query sorted |
| Different child or field | untouched | one answer per child *per field* |

The review queue also now shows the **group** the answer was asked of
(`audience_label`) rather than the class on the request row — a house link has
no class at all, so the old reading would print a dash on every one of them.

## 3. B-37 — the flag was on four rows out of four

Found by building the scenario and looking at the result, not by a test.

The first version read "what is held now" from `student_records` only, with a
comment claiming that avoided flagging everything. It did the opposite: a value
the teacher was shown that came from the **fee column** has no `student_records`
row, so "no row" was indistinguishable from "the value was cleared" and every
such answer was called stale. Four flags on four pending rows in the dev
fixture — a flag on every row is a flag nobody reads.

Two things were wrong, and both needed fixing:

1. **The read** now follows the same precedence the link itself used —
   VPPS One's own accepted answer, then the fee column — through the same
   `heldValue()` the gap filter and the freeze use.
2. **The rule** now requires something to conflict with. "She was shown a
   number and we hold nothing now" is not stale: accepting fills a hole, and
   there is no correction to revert. The warning exists to stop the office
   silently undoing somebody's correction, so with no current value there is
   nothing for it to say.

After the fix: **2 flags**, both genuine, on the two answers whose value the
office really had corrected since.

catches a flag stuck on — asserts the stale flag is **absent** before the
correction is made, and present twice afterwards.

## 6. What R3.4 still owes

- **Mock message retry.** The mock provider and its outcomes by last digit
  exist from R0.2 (`provider.ts`: sent / slow / timeout / rate-limited / server
  error / duplicate) and `selectProvider()` refuses `mock` on live. What is
  missing is the retry path in the send queue that those outcomes exist to
  exercise.
- **S-01–S-09 acceptance.** A pass over the SamPark rows with evidence for each,
  rather than the per-task claims made so far.
- **Precedence between sources on accept.** `mayReplace()` has existed since
  Phase 5 and the accept path does not consult it. Nothing imports yet, so it
  cannot currently be wrong — but it is not wired.
- A superseded answer is greyed and still decidable. Refusing it outright would
  be the office's decision to lose, and nothing yet says which is wanted.
