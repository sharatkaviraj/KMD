# Decisions

Settings, not facts to re-derive. Add a row rather than arguing a point twice.
An agent that picks a default the plan left open records it here.

| # | Decision | Why |
|---|---|---|
| D-1 | VPPS One is a separate repo, Vercel project and Postgres schema from the fee app | The first attempt guarded the fee *module* but changed 45 shared platform files. A boundary enforced by structure cannot be forgotten; one enforced by review can |
| D-2 | No feature flags, no canary users, no release types, no approval gates | They existed only to protect `director@` from shared code. There is no shared code now |
| D-3 | Build on `schoolfees-dev` (`wtgxcptmucjerhufzjcf`) with test-session data; cut over to live at the end | Janmejay's call. Lets the whole app be built and used before any real data is involved |
| D-4 | Everything VPPS One owns lives in the `vppsone` schema | Makes the cutover additive-by-construction and collisions impossible |
| D-5 | Fee tables are SELECT-only, and no constraint points into `public` | A foreign key would be a write into the fee app's schema |
| D-6 | VPPS One has its own roles, not `public.users.role` | Being an accountant in the fee app says nothing about teaching |
| D-7 | Push to main through a PR the agent merges when CI is green | Keeps CI honest without adding a person-shaped wait |
| D-8 | Local folder is `Desktop\vppsone`, not `VPPS one` | npm refuses spaces and capitals in a project directory name |
| D-9 | Supabase Storage for files; Cloudflare only if storage or egress cost bites | One fewer service to run |
| D-10 | Parent-facing WhatsApp stays human-pressed | Unchanged from the original plan |
| D-11 | `office` may manage staff profiles, not just read them | PLAN §3 gives office the master data and PROGRESS 1.3 files staff under it. A profile is not an account — `user_id` is nullable and logins are created in Supabase Auth by an admin — so editing one cannot grant anybody access |
| D-12 | The root file is `src/proxy.ts`, not `middleware.ts` | Next.js 16 renamed the convention and deprecated the old name. The fee app is already on `proxy.ts`, so this matches what is running in production |
| D-13 | Writes have no RLS policy at all; server actions check the permission and then use the service-role client | Keeps "who may write" in one readable TypeScript file instead of spread across policies a role change would have to be kept in step with. The SELECT policy still governs every read |
| D-14 | Permission names are the whole platform's, not only Phase 1's | Six role lists written a phase at a time drift apart. Naming the full surface once makes the map readable as a whole, and `can()` is exhaustively tested against it |
| D-15 | `view_only` gets dashboards, not every `:view` | "Read-only dashboards" (PLAN §3) is oversight — the daily numbers and who teaches what. It stops short of per-child records: no notes, marks, documents or collection |
| D-16 | An unknown role resolves to `view_only`, never to anything higher | A role added to the `staff_role` enum before the code that understands it must not be able to arrive as an admin |
| D-17 | `short_name` immutability is a database trigger, not only a form rule | It is the timetable's join key; a rename orphans every slot that named it. A server action can be rewritten, a trigger cannot be forgotten |
| D-18 | `short_name` is unique case-insensitively | "RKS" and "rks" are the same teacher to everyone except a plain unique constraint, and a case-variant duplicate is a silently wrong timetable import |
| D-19 | Exposing the `vppsone` schema to PostgREST is a migration file, applied additively | Creating the schema is not enough — PostgREST answered `PGRST106 Invalid schema` until it was exposed. It has to be replayed at cutover like any other migration, and it appends rather than replaces so the fee app keeps `public` |
| D-20 | `getCurrentStaff()` is cached per request, not across requests | The fee app caches the profile for 60s because of its traffic; this app has a few dozen users, so a role change or a deactivation should take effect on the next navigation |
| D-21 | Signed in with no staff profile is a named state, not an error | VPPS One shares `auth.users` with the fee app, so any fee-app account can sign in here and succeed. The login page says why instead of failing blankly |
| D-22 | Migration files are named for the version the Supabase MCP recorded | The MCP assigns its own timestamp. Naming the file to match keeps the repo and the database's history in exact correspondence for the cutover replay |
| D-23 | The proxy sends signed-out visitors to `/login`, but never sends signed-in ones away from it | The proxy has a JWT, not a profile. Bouncing on the JWT loops forever against a session whose profile was deactivated, and every hop runs the page. The login page already decides this from the profile, so one authority instead of two disagreeing ones |
| D-24 | The design system is the fee app's "Ledger Calm" palette, ported to Tailwind v4 `@theme` | The same staff use both apps on the same phones. A second visual language is a second thing to learn, for no gain |
| D-25 | Signed-in screens live in the `src/app/(app)/` route group, guarded by its layout | Makes the guard structural: a new screen is protected by where its file sits, not by somebody remembering a call at the top of it |
| D-26 | Navigation is derived from `can()`, and each item carries a `ready` flag | One map for access and for navigation, so they cannot drift. `ready` exists because the phase ships over several deploys — a tab whose route has not landed is a 404 with the school's name on it. A test asserts the flag matches a real page file, in both directions |
| D-27 | Pages use `requirePermission()` (redirects); server actions use `assertPermission()` (throws) | `redirect()` works by throwing a navigation signal, which a `try/catch` inside an action would swallow — and a swallowed guard is a guard that passed |
| D-28 | A navigation bar with fewer than two tabs is not rendered | Its only job is showing where else you could go. With one tab it says nothing and costs 68px of a phone screen |
| D-29 | Staff search filters in the browser, over the whole list | A school has a few dozen staff. One fetch and instant filtering beats a round trip per keystroke, and it keeps working where the signal is worst — which is the corridor, which is where it is used |
| D-30 | A phone number that is not a 10-digit Indian mobile is refused, not stored as typed | Phase 5 messages these numbers. A wrong number that looks right is worse than a blank |
| D-31 | Staff are deactivated, never deleted | The timetable, attendance and marks all reference the profile, and `short_name` is the join key. Inactive means "not in the pickers", not "never existed" |
| D-32 | Fee-table reads go through the service-role client, after `assertPermission()` in the repository function itself | The fee app's RLS gates `public.classes` and `public.students` on `has_any_permission()`, which reads `public.users.role`. VPPS One staff have no row there (D-6), so a cookie-client read returns zero rows **and no error** — which renders as "the school has no classes". A policy would fix it and rule 2 forbids adding one to a fee table, so the guard moves into the app. It sits in the repository rather than the caller so a future call site cannot forget it |
| D-33 | The class-label editor saves one row at a time | Nineteen classes get filled in over more than one sitting. A single form with one Save at the bottom loses the lot to an interruption |
| D-34 | The academic session is derived from the fee app's class rows, not configured | There is no `public.sessions` table; the label lives on each class. Deriving it means the cutover follows the real session with no variable to remember. `VPPSONE_SESSION_LABEL` overrides it for the weeks when two sessions overlap |
| D-35 | Language is a property of the account — `hi`, `en` or `both` — not of the app | Janmejay's call. The school is not one audience: a teacher in the village reads Hindi, the office reads English. Showing everybody both made every label twice as long for every person and gave nobody the screen they wanted. Strings are written once as a pair and rendered per reader |
| D-36 | The login screen's language comes from a device cookie written at sign-in; a first-ever visit gets `both` | Signed out there is no profile to read. Bilingual is the only choice that cannot lock somebody out of the one screen they must be able to read. Ported from the fee app, which reconciles `preferred_locale` to a cookie for the same reason |
| D-37 | Dense surfaces — nav tabs, list rows, the browser tab title — lead with one language even for a `both` reader | A tab is ~70px and a title bar truncates. Two lines there is not bilingual, it is unreadable. Detail views, notices and form labels show both |
| D-38 | Validation messages cross the Zod boundary as JSON-encoded pairs | A schema is parsed in a server action, long before a component exists, so it cannot know the reader's language. JSON rather than a delimiter because a name or class label could contain any separator, and a message that splits in the wrong place is worse than one left untranslated |
| D-39 | A calendar day says *both* whether school is open and whether the timetable runs | They are not the same question. On an exam or an event day children come in and the register is taken, but no period runs. Collapsing the two would mean either an exam day with no attendance recorded, or a holiday that still expects a register |
| D-40 | Only non-ordinary days are stored; absence of a row means the weekly pattern | A year is a few dozen rows rather than 365, and adding a holiday is one insert. The weekly pattern is Sunday closed, **Saturday open** — the thing a general-purpose calendar library gets wrong for this school |
| D-41 | A class-teacher handover closes the old row on the day before the new one starts | Two open rows would mean "who is the class teacher today" has two answers. The partial unique index refuses it, and the close-then-open order means a failure leaves a class visibly empty rather than permanently blocked |
| D-42 | A calendar range is expanded to one row per day, not stored as a range | Every other screen asks about one day — "is school open on the 14th". A stored range would make that question a join, on the hottest read in Phase 3 |
| D-43 | A rebuild never deletes an enrolment whose student the fee app has lost | That child still has attendance and marks recorded here. Dropping the row would orphan history that is still true, so the consistency check reports it and a person decides |
| D-44 | Enrolments are rebuilt on a button, never on a schedule | A rebuild resolves every difference by taking the fee app's word for it. A child moved yesterday and a child moved by mistake look identical to the code and completely different to the office |
| D-45 | A class change and a roll change on the same child are one difference, not two | A child who moved class almost certainly has a new roll number. Reporting both would double-count one event and make the list look worse than it is |
| D-46 | The parser reports problems; it does not reject a sheet | Task 2.2 has to show the school what is wrong before anybody publishes. A short row still parses as far as it goes, so one bad line shows as one bad line rather than an empty screen |
| D-47 | `SHORT_SUBJECTS` is not ported | `docs/SOURCES.md` says it is applied at render time and that applying it while parsing produces labels matching no subject row. A test asserts the long spellings survive the parse |
| D-48 | The import dry run keeps going after the first unresolved name | A run that stopped at the first unknown teacher would make the school fix one, re-upload, and find the next — nineteen times |
| D-49 | Publishing archives the previous version before publishing the new one | The partial unique index allows exactly one published version per session, so the other order is refused. Closing first means a failure leaves the session briefly unpublished — visible — rather than permanently blocked |
| D-50 | `teaching_assignments` is regenerated last in a publish, and replaced wholesale | Last, so an interruption leaves stale assignments for a live timetable rather than assignments for one that is not live. Wholesale, because an assignment the new timetable does not contain must disappear, and a diff would put the rule in a second place |
| D-51 | "Who is free" takes the whole teaching roster, not the teachers on the timetable | Somebody with no periods at all is the *most* free. Deriving the roster from the timetable is exactly the bug `timetable2025` worked around with a hard-coded reserve list |
| D-52 | Every screen under `(app)` must be a nav tab or listed in `NON_NAV_SCREENS` | The `ready` flag only guards items already in the nav list, so a screen left out entirely was invisible to it — which is how `/timetable` was briefly unreachable. A test now requires one or the other |
| D-53 | Which session it is, and what a class is called, are gated on *being staff* — not on `academics:view` | A teacher has no `academics:view`; it guards the screens that *edit* master data. Gating the session label on it meant a teacher opening their own register was refused before a single mark could be read. A class is called "Class 6 A" and knowing that is not a privilege |
| D-54 | `on_behalf_of` names the teacher the office stood in for, never the person pressing the button | `taken_by` already records who pressed it. Setting both to the same person makes the two columns agree and records nothing — which is the one fact the column exists to keep |
| D-55 | The monthly register prints; there is no PDF renderer | The browser already owns the paper size, the margins, the preview and the Devanagari fonts, and on every device the school uses "print" is also "save as PDF". A server-side renderer would mean shipping all four again to produce a worse copy of the same table |
| D-56 | Fee figures appear on the student card only for `collection:view` | A teacher does not need a family's dues in order to teach, and putting them on a screen opened in a corridor invites the conversation the office should be having. Fees and late fees stay separate figures either way (D-33) |
| D-57 | The offline queue is an external store read through `useSyncExternalStore`, not component state | `localStorage` changes without React knowing and has to be read on mount. As component state that means `setState` inside an effect — a cascading render, and the lint rule that caught it was right. It also makes a second tab's writes visible for free |
| D-58 | A `Localized` pair whose halves are identical renders one line, not two | Proper nouns are most of them: a class is "Class 6 A" and a teacher is their name in either language. "Class 6 A · Class 6 A" looks broken to exactly the readers who asked to see both |
| D-59 | The Today card distinguishes three kinds of nothing — school closed, no class of your own, everything already in | A card that counts rows renders all three as an empty box, and only one of them means "you are finished". Telling a teacher they are free when they are not is the failure this screen exists to prevent |
| D-60 | Marks are not on the student card yet, and there is no placeholder for them | PLAN 3.5 names them, but the assessment tables arrive in Phase 6.1. An empty section promising marks is a promise the data cannot keep |
| D-61 | The substitution engine is ported whole, minus its `localStorage` plan store and its two hard-coded name lists | The ranking, the tiers, the weights and the min-cost flow have run this school's cover for a year and came across unchanged. What did not: `createPlanStore` (plans are rows here, so pruning is a query and invalidation is `substitution_plans.version_id`), and `DEFAULT_SHIFTS` / `RESERVE_STAFF` / `DUTY_STAFF`, which named real teachers in source — rule 6 forbids that here, and a school that cannot change its own part-time hours without a deploy is worse off anyway. They are rows in `cover_policies` (task 4.4) |
| D-62 | Any read that can exceed a thousand rows is paged through `fetchAllRows()` | PostgREST caps a response at `max-rows` — 1000 on Supabase — with **no error and no warning**. The published timetable is 1038 slots, so `listSlots()` had been returning 1000 of them since Phase 2: thirty-eight lessons missing from every timetable view and invisible to the planner. The worst shape a limit can take is the one where every caller still looks correct |
| D-63 | A role with more screens than the bar holds gets a "More" hub as its fifth tab | The cap is five, because a sixth on a 360px phone puts every tab under 60px. The old `slice(0, 5)` met the cap by dropping the sixth screen entirely, which is how `/substitutions` became unreachable for admin, office and the academic coordinator the day it was added — the same class of bug as `/timetable` shipping with no tab. A test now asserts that everything a role may open is reachable somewhere |
| D-64 | A vacancy is one per class and period; a shared block absorbs an absence, a parallel elective does not | ELGA is one activity with five teachers, so one away leaves four teaching and no cover is needed. "Biology / Maths (X / Y)" is two lessons side by side with one cohort each, so one away leaves a cohort with nobody even though somebody is standing in the same room. One vacancy per (class, period) even when both halves of a parallel cell are away: the room needs one cover teacher, and the unique index says the same |
| D-65 | Publishing a plan notifies the covering teachers in the app, on their own Today card — not by WhatsApp | A cover nobody was told about is a class nobody turns up to, so publishing has to reach the teacher. An outbound send is a different thing with a different cost and a different failure mode; the AiSensy integration arrives in Phase 5.4 and the scheduled nudges in 7.2, and until then the app is where the school already looks each morning |
| D-66 | Anything a coordinator sets by hand is pinned by construction, and a pin survives regenerating | They decided it. The reason to work the cover out again is that something changed *around* their decision, not that they want it undone — so the pinned rows are read first, everything else is cleared, and the engine is handed the pins as work already done so it never double-books against one |
| D-67 | The seed scripts load the app's own parser and engine from source, through a 15-line `@/` resolver hook | Node 24 runs TypeScript by stripping types, which is enough for modules that are logic and types and nothing else. A reimplementation in `scripts/` would be a second parser and a second engine to keep in step, and seeded data the app could never have produced is worse than no seeded data. `plan.ts` and `labels.ts` are split along that line for this reason |
| D-68 | The token links are public by design, and the token is the whole authorization | The school has forty staff and four accounts. Asking the other thirty-six to remember a password is asking them not to answer, which is the problem Sampark was built to solve. Open is not unguarded: ~96 bits of entropy, one request per token and no navigation past it, every rejection the same 404, and a guess rate limited in Postgres with its own budget so a teacher never spends a guesser's and a guesser never hides inside hers |
| D-69 | An accepted answer lands in `vppsone.student_records`, never in the fee app | Sampark wrote master fields straight back to its own `students` table; rule 2 forbids that here. So `collection_fields.fee_column` is a **comparison**, not a destination: the form shows a teacher what the fee app holds, the review queue says when the two disagree, and a person changes the fee app deliberately, in the fee app |
| D-70 | An approved human answer outranks every import, forever, and the rule lives in code | A row can be edited, and no administrative convenience is worth the day a teacher discovers her approved correction was quietly undone by somebody re-importing last term's export. That is the difference between the tool being trusted and being abandoned |
| D-71 | A repeated phone number is never an error | Siblings share a parent's number — 134 numbers in the school Sampark was built for, 133 of them spanning more than one class. A uniqueness check would refuse the correct answer and teach a teacher the screen is wrong about her own class. The office sees a neutral "also on N other children" count; the teacher sees nothing |
| D-72 | Blank always means "no change", never "erase" | A teacher who skips a child has not answered for them. A form that read a skipped box as a deletion would empty a register on its first pass, and the register is what everything else is built on |
| D-73 | The review queue splits changes from confirmations, and confirmations are accepted in bulk | "This is already right" is a real and useful answer — somebody looked — but it is not a change, and a queue that made the office approve four hundred of them one at a time is a queue nobody finishes |
| D-74 | The public link renders in the language of the teacher it was made for | She has no session to read a preference from, so the language travels with the request. Rule 9 does not stop applying because somebody is not signed in |
| D-75 | A student document lives in a private bucket and is served through a signed URL that lasts a minute | A birth certificate with a guessable URL is a birth certificate anybody has. The path is keyed by child and by a random id rather than the filename, so two parents both sending `aadhaar.pdf` cannot collide and nothing is guessable. The permission is checked inside the function that mints the URL, because that is what hands out the capability |
| D-76 | A parent-facing message is never dispatched by the app | D-10, now executable: `mayDispatch()` refuses it whatever the screen believes, and the office opens it in their own WhatsApp instead. The day an automatic send goes out wrong it goes out wrong to four hundred families at once, with no recall. Staff messages may go through the provider, and even those need an `AISENSY_API_KEY` this repo does not carry — sending costs money, which rule 8 makes somebody else's decision |
| D-77 | "9 of 45" is a function, not two numbers around a translated "of" | English counts up from the part, Hindi counts down from the whole: `45 में से 9`. Interpolating in one fixed order renders backwards in one of the two languages, which is how the attendance register shipped wrong in Hindi in Phase 3 — caught in Phase 5 on a page that happened to render for a Hindi reader |
| D-78 | An exam has a paper per class per subject, not one max mark | PLAN §5 says "exams, subjects, max marks" as though a max belonged to the exam. It does not: a Class 5 English paper and a Class 10 English paper are different papers out of different totals, and one `max_marks` on the assessment would make the whole school sit the same one. `assessment_subjects` is the extra table that makes the rest of the phase possible |
| D-79 | A mark has three states, and every screen shows all three | Blank is nobody has entered it yet, Absent is a child who did not sit the paper, and a number is a number — including nought, which is a real mark somebody gave. A grid that collapsed blank and nought would make "who has not entered yet" unanswerable, which is the question the whole board exists to answer. `isEntered()` is the one place the rule lives, and the check constraint `marks_absent_has_no_value` stops the database holding two answers at once |
| D-80 | Every change to a mark is logged with both sides of it, and an unchanged save writes nothing | A mark that changes after a parent has seen it is the most sensitive write in this app, so "it was 68 last week" gets an answer that does not depend on anybody remembering. The log is append-only. A save that changes nothing is not a change, and a log padded with them is a log nobody reads |
| D-81 | A paper nobody has marked is out of both halves; an absence is a nought it is out of | Counting an unmarked paper as zero hands a family a percentage the child did not earn, and the mistake looks exactly like a bad result. An absence is different: the child sat the term and did not sit the paper, which is a real nought on a real report. The two cases are one line apart in `totalsFor()` and are the arithmetic everything else inherits |
| D-82 | A report card is a snapshot, not a view | A card is what the school handed a family on a day. Marks move afterwards — a correction, a re-mark, a paper found under a desk — and recomputing the card from today's marks would silently rewrite what a parent is holding. So an issued card stores its own copy of every number and grade it printed, and a reprint is a new card somebody asked for rather than yesterday's card quietly moving. `previewReportCard()` and `issueReportCard()` are separate functions for exactly this reason |
| D-83 | Weight applies to the percentage, never to a printed mark | A paper is out of what it is out of, and a family reading "34 out of 40" must see the number the teacher wrote — so `scored` and `outOf` stay the plain sums and add up by hand. What a school means by "the half-yearly counts double" is that it counts double *towards the term*, which is the percentage. `totals.weighted` says whether it changed anything, so a card only explains itself when the weights actually differ. This was written down before it was true: the column and the form field shipped applying to nothing, and the smoke test on seeded data is what caught it |
| D-84 | The grade bands are a default, and the screen says so | Nobody has told us what this school's bands are. Inventing them silently would put a letter on a document a family keeps, on somebody else's authority — so the bands are in one exported constant, the report screen carries a line saying they still need confirming, and changing them is one edit rather than a search |
| D-85 | There is no report card PDF — the browser prints it | PLAN 6.4 says "PDF". A print stylesheet is what a school with one printer and a phone in every pocket actually uses: nothing to install, nothing to generate server-side, and the page a coordinator checked on screen is the page that comes out. A PDF endpoint would be a second renderer to keep in step with the first, for a file nobody asked to store |
| D-86 | The app accepts a link Supabase minted, not only a password | `/auth/confirm` is the standard `token_hash` door, and it is the one the school actually needs: forty staff, four accounts, and the reason for that gap is not secrecy but that asking thirty-six people to remember a password is asking them not to use the thing (D-68). It cannot be used to *request* anything — there is no "send me a link" form anywhere, and only the service role can mint a token — so the endpoint is inert until somebody deliberately issues one. Both doors run the same `admitSignedInUser()`, so the profile and active checks cannot drift apart |
| D-87 | The signed-in screens are verified by signing in, with passwordless test accounts | Every phase from 3 to 6 shipped with nobody having looked at the authenticated screens; they were covered by route guards, SQL probes and unit tests, which is not the same thing. `npm run dev:login` mints a one-time link for a `@qa.vpps.local` account, refuses any other address, and refuses to run outside dev. The first pass through it found two bugs that no probe would ever have caught (D-88, D-89) |
| D-88 | A note that a screen works offline is not the same sentence as a report that it is offline | The Teach card rendered `attendanceOffline` — "there is no internet" — unconditionally, so every teacher on a working connection was told she had none. Present-tense status and standing capability are two messages, and the register form's conditional use of the first one was right all along |
| D-89 | A missing mark row and a blank mark row are the same state | `saveMark()` required an existing row before it would call a save unchanged, so a teacher who filled in one child and saved wrote a change-log entry for every child she had not reached — each reading "not entered → not entered" — and left an empty row behind for each. The comparison moved into `markChanged()` in the domain, where it is one function with tests, rather than a condition in a repo nothing could reach |
| D-90 | One run of a job at a time is a partial unique index, not a flag in the application | A lock held in memory does not exist when the application is two instances, which on Vercel it always is — two overlapping register-opening runs would each find no register and each create one. `job_runs_one_at_a_time` makes the database refuse the second insert, and the repo reads that refusal as "already running" rather than as an error, because two crons overlapping on a redeploy is an ordinary thing that happens |
| D-91 | A job that already succeeded today is skipped, and only a person can override it | This is what makes a cron that fires twice harmless — a retry, a redeploy, two regions. A failed run does not count as done, so the retry still runs, and a *skip* does not count either: treating it as the success would make a job that failed once look like a job that has worked every day since. The console's button forces it on the second press, after the first has said why, because opening a second set of registers should take two decisions |
| D-92 | Each job has its own token, derived from one secret, and an unconfigured deploy runs nothing | `HMAC(JOBS_SECRET, job)` gives four different tokens and none of them is the secret, so one can be handed to whatever triggers one job without handing over the other three, and a token that leaks out of a cron dashboard reveals nothing about the rest. Vercel's own `CRON_SECRET` bearer is accepted alongside it. With neither variable set the route refuses everything rather than accepting everything — "the jobs never ran" is a discoverable problem in a way that "anybody could run the jobs" is not. Every refusal is the same 404, so a guesser cannot learn which job names exist |
| D-93 | A job that swallows a query error reports a confident zero, so every read fails loudly | `attendance-reminder` reported "19 classes have no class teacher" on its first run. That was not a finding about the school: the query named `from_day`/`to_day` on a table whose columns are `effective_from`/`effective_to`, PostgREST returned an error, and `const { data } = await …` dropped it. A second wrong table name was hiding behind the same silence. Every read in `job-work.ts` now goes through `must()`, which throws — and `runJob()` turns that into a failed run somebody can see, rather than a cheerful number nobody questions |
| D-94 | A reminder is deduplicated per template, not per person | The first version skipped anybody who had received *any* message that day, so a teacher nudged about outstanding marks silently stopped being asked about her register. Two jobs ask two different questions about two different pieces of work, and "already asked" has to mean already asked *this* |
| D-95 | An embed names its foreign key whenever a table points at another one twice | `message_sends` references `staff_profiles` from both `requested_by` and `staff_profile_id`, so `staff_profiles(display_name)` has no answer: PostgREST refuses with "more than one relationship was found" rather than picking one. `/collection/messages` shipped in Phase 5 with that select and threw on every load until somebody signed in and opened it. Nothing else could have caught it — it typechecks, it is not a data problem, no unit test reaches PostgREST, and a SQL probe issues different SQL than the app does. `tests/embeds.test.ts` now reads the foreign keys out of the migrations and the selects out of the repos and compares them, so the check grows with the schema instead of being remembered |
| D-96 | A check that finds nothing has not passed, it has broken | Said twice in one day and worth writing down. The cutover check printed a tick after its regex was mangled and it found zero tables; `tests/embeds.test.ts` passed against the exact bug it was written for, because the repo is checked out CRLF on Windows and every pattern anchored on `\n` silently matched nothing. Both now assert that they found something before they report on it, and a new check gets tried against the broken state before it is trusted |
| D-97 | A guard that fires mid-stream cannot set a status code, and the smoke test has to know that | Once the shell has started streaming, `redirect()` in a Server Component emits `<meta id="__next-page-redirect" http-equiv="refresh">` instead of a 307. Read the status alone and every refusal in the app looks like a page that rendered — which is what the first run of `smoke:roles` concluded, about all six roles at once, and it would have been reported as a catastrophic permission failure. The classifier reads the meta tag. The side effect worth knowing: a refused screen shows its shell for about a second before bouncing, because the page began rendering before the guard resolved |
| D-98 | Every screen is opened as every role, and the expected answer is read out of the screen's own guard | `permissions.ts` says who may open what, and a unit test that checked a page against that map would be asserting the map against itself. `npm run smoke:roles` takes the permission out of each page's own `requirePermission()` call, works out what the map says should happen, signs in as all six roles and finds out what does — thirty-six screens by six roles, which is more combinations than anybody checks by hand and where the interesting ones are always the boring ones nobody thought to try |
| D-99 | A page guard does not guard the action underneath it | A Server Action is a separate POST to a generated endpoint, reachable by anybody holding the action id whether or not they can open the page it came from. The page and the action are two doors into the same room. `tests/action-guards.test.ts` reads the body of every exported async function in a `"use server"` file and requires a check inside it, with two files exempt on purpose: signing in, and the public collection link where the token is the authorization (D-68) |
| D-100 | A skipped run is written down | Returning quietly left the console unable to tell "the cron fired at 7:15 and found the work already done" from "the cron never fired at all" — and which of those it is happens to be the only question the console exists to answer. The skip row carries no summary, because the status badge already says "Already done" in the reader's own language; the card shows the numbers from the last run that actually did something, which is a different row whenever the last attempt was a skip |
| D-101 | Nothing is outstanding on a day the school was shut | The daily summary subtracted submitted registers from the number of classes, so every Sunday reported nineteen registers outstanding — nineteen teachers apparently having failed to take one, on a day nobody was there. Found by running the job for a Sunday rather than by reading it |

A link written from memory would hand a member of staff a stranger's login form. The wrong hostnames are listed in code as `FOREIGN_ORIGINS` so a test can refuse them, and the right ones carry a string to look for in the response — because "the host answered" is not "the host is the application we meant" |
| D-109 | An origin's `environment` describes the **dataset behind it**, not its Vercel target, and an id may not cross datasets | VPPS One's Vercel *production* deployment is a `dev` origin, because rule 3 keeps it on schoolfees-dev. Both siblings are on live data. So every VPPS One → sibling deep link today crosses a boundary where the student id means nothing, and rule 3 forbids connecting to the live fee database to check. `idsTravelBetween()` returns false for every such pair and R1.1 builds the search-screen fallback around that, rather than shipping id-bearing URLs and discovering the 404s in testing |
| D-110 | The client-JS ratchet is measured from `.next/static`, not from the build output | Next.js 16.3.5 with Turbopack prints the route table without a First Load JS column, so the number PLAN §5 R7 asks to ratchet is not in the build log. `find .next/static -name '*.js' -printf '%s\n'` after a production build is reproducible and is what the R0.1 baseline of 1,293.2 KB across 37 files was taken with |
| D-111 | A missing sibling test environment is recorded as a gap, not engineered around | School Fees preview deployments do point at schoolfees-dev, which looked at first like the fee sandbox R6.2 needs — but every preview URL answers `302 → vercel.com/sso-api`, so it is not a destination a member of the office could open. SamPark has no test deployment at all. Inventing a substitute (a local fee app, a mocked destination) would produce evidence about something staff will never use, so R6.1 links the live fee app with an explicit label and R6.2 stays blocked on somebody creating a real one |
| D-112 | The QA teacher is bound to a teacher the published timetable already knows, chosen by rule rather than named in the repository | A teacher's periods come from `timetable_slots`, so an account the sheet has never heard of has no day no matter what else is written for it — which is why `qa.teacher@` could hold nothing for seven phases and 216 smoke combinations without anybody noticing (B-17). Giving it a day by editing the published timetable would corrupt the sheet; giving it one by binding the login to a profile the sheet already contains costs one column. The pair is picked by "most periods, ties by short name, second must share no class with the first" so that no member of staff is named here (rule 6) and the choice survives a new timetable. It refuses rather than pairing two teachers who overlap, because a fixture whose two teachers share Class 8 makes every cross-teacher leak test pass for the wrong reason |
| D-113 | Every QA fixture write records its previous value, and `qa:reset` replays the log backwards | The seeder has to touch rows it did not create, so "delete what I made" is not enough and "set it back to null" is a guess that quietly eats whatever was there. The undo log is also the only way PLAN §5 R0's "fixtures removable by run ID" and QA.md's "verify cleanup" can be answered with evidence instead of a claim: the proof that it works is 11 steps out, 11 steps back, the database compared row by row, and 11 steps out again picking the same two teachers. An unchanged save writes nothing and logs nothing (D-80), so a second seed records zero steps rather than filling the log with restorations of a value to itself |
| D-114 | The fixture cannot invent children, and says so rather than finding a way | The roster is `public.students` and rule 2 makes it SELECT-only. Emptying a class is possible because leaving is a VPPS One fact (`enrolments.status`), so `--edge-classes` can build a class of none and a class of one; a 40-child class and the 1,205-row list QA.md asks for cannot be built from here at all. Seeding the fee dev database is somebody else's decision, and the row-cap risk that made this matter (D-62) is already covered by the 1,038-row timetable read and `tests/paginate.test.ts` |
| D-115 | Which provider sends is chosen by `MESSAGE_PROVIDER`, the mock is refused on a live deployment, and every mocked id carries a `mock:` prefix | QA needs a 429, a timeout and a duplicate on demand, and a test student does not make a recipient phone a test phone (PLAN §1) — so the outcome comes from the destination's last digit and no packet leaves. Two guards make that safe rather than dangerous: a live deployment refuses the mock outright, because writing `sent` rows for messages nobody received would be discovered by a parent rather than by us; and the `mock:` prefix lands in `message_sends.provider_message_id`, so a row that was never really sent can never be read as one by a screen, a later query, or somebody reading the table at cutover. `duplicate` returns the **same** id every time, which is what makes a replayed delivery callback testable at all |
| D-116 | `periodNumber()` is the only place the period off-by-one lives | The sheet's first column is index 0 and `timetable_slots.period` stores it, so every screen has to add one. Six screens each remembered; the teacher's Today card — the screen she opens every morning — did not, so her first lesson read "0" and her last read "7". It shipped in Phase 3.1 and nothing could catch it, because the only teacher account in the test data had no periods to render. The fix is not the `+ 1`, it is removing the thing to remember: one function, used everywhere, and a test that scans every component for a hand-written `period + 1` and for a raw `{…period}` rendered as JSX children |
