# Decisions

## Opening the app faster — 6 November 2026

Janmejay asked for the app to boot faster and more smoothly, from the logo to the first screen, on phones (installed) and laptops. The speed logs showed first paint landing with the first byte on almost every first open: nothing reached the phone until every read of the frame was done.

| Decision | Outcome | Evidence and reason |
|---|---|---|
| D-461 | **The root layout waits on nothing slow: `<html>`, the styles and a boot splash go out at the first byte, and everything that reads the account streams in behind a Suspense boundary** | Before, the root layout resolved the locale (a staff read when the `vpps_locale` cookie is absent) and the (app) layout and shell did every read before one byte was sent, so an installed app sat on the system splash and a browser tab on a white page for 0.8 to 4 s on a normal day. The splash (`src/ui/system/boot-splash.tsx`) uses the manifest's paper colour and the crest, so the hand-over from the phone's own splash is invisible; it is HTML and CSS only, says "Still loading" by itself after 8 s, and follows dark mode because next-themes stays above the boundary. `<html lang>` comes from the cookie when there is one; otherwise a one-line script inside the stream corrects it from the account before any screen text arrives. A redirect from the (app) layout (a missing or inactive profile) now streams instead of answering 307; the proxy still answers 307 for everybody signed out |
| D-462 | **Opening `/` goes straight to the person's home from the proxy, by a home hint cookie (`vx_home`)** | The installed app always opens `/`. For everyone but the admin menu `/` only redirects (to `/teach`, `/accounts`, a chosen start screen), and that redirect came after the layout and shell had done all their reads: two full signed-in renders on every open for a teacher. The shell now writes where `/` would send this person (`src/vx/home-redirect.ts`, the same rule the page uses) as `user id + path`; the proxy follows it only for that same account, only for a plain document load of `/` with no query (never a client navigation or prefetch), and only to a safe internal path. It is a hint, never a grant: the screen it opens checks its own permission. Stale after a role or start-screen change for one open at most, and the screen it lands on rewrites it. Never written while an admin previews another role |

| D-90 | One run of a job at a time is a partial unique index, not a flag in the application | A lock held in memory does not exist when the application is two instances, which on Vercel it always is — two overlapping register-opening runs would each find no register and each create one. `job_runs_one_at_a_time` makes the database refuse the second insert, and the repo reads that refusal as "already running" rather than as an error, because two crons overlapping on a redeploy is an ordinary thing that happens |
| D-91 | A job that already succeeded today is skipped, and only a person can override it | This is what makes a cron that fires twice harmless — a retry, a redeploy, two regions. A failed run does not count as done, so the retry still runs, and a *skip* does not count either: treating it as the success would make a job that failed once look like a job that has worked every day since. The console's button forces it on the second press, after the first has said why, because opening a second set of registers should take two decisions |
| D-92 | Each job has its own token, derived from one secret, and an unconfigured deploy runs nothing | `HMAC(JOBS_SECRET, job)` gives four different tokens and none of them is the secret, so one can be handed to whatever triggers one job without handing over the other three, and a token that leaks out of a cron dashboard reveals nothing about the rest. Vercel's own `CRON_SECRET` bearer is accepted alongside it. With neither variable set the route refuses everything rather than accepting everything — "the jobs never ran" is a discoverable problem in a way that "anybody could run the jobs" is not. Every refusal is the same 404, so a guesser cannot learn which job names exist |
| D-93 | A job that swallows a query error reports a confident zero, so every read fails loudly | `attendance-reminder` reported "19 classes have no class teacher" on its first run. That was not a finding about the school: the query named `from_day`/`to_day` on a table whose columns are `effective_from`/`effective_to`, PostgREST returned an error, and `const { data } = await …` dropped it. A second wrong table name was hiding behind the same silence. Every read in `job-work.ts` now goes through `must()`, which throws — and `runJob()` turns that into a failed run somebody can see, rather than a cheerful number nobody questions |
| D-94 | A reminder is deduplicated per template, not per person | The first version skipped anybody who had received *any* message that day, so a teacher nudged about outstanding marks silently stopped being asked about her register. Two jobs ask two different questions about two different pieces of work, and "already asked" has to mean already asked *this* |
| D-95 | An embed names its foreign key whenever a table points at another one twice | `message_sends` references `staff_profiles` from both `requested_by` and `staff_profile_id`, so `staff_profiles(display_name)` has no answer: PostgREST refuses with "more than one relationship was found" rather than picking one. `/collection/messages` shipped in Phase 5 with that select and threw on every load until somebody signed in and opened it. Nothing else could have caught it — it typechecks, it is not a data problem, no unit test reaches PostgREST, and a SQL probe issues different SQL than the app does. `tests/embeds.test.ts` now reads the foreign keys out of the migrations and the selects out of the repos and compares them, so the check grows with the schema instead of being remembered |
| D-96 | A check that finds nothing has not passed, it has broken | Said twice in one day and worth writing down. The cutover check printed a tick after its regex was mangled and it found zero tables; `tests/embeds.test.ts` passed against the exact bug it was written for, because the repo is checked out CRLF on Windows and every pattern anchored on `\n` silently matched nothing. Both now assert that they found something before they report on it, and a new check gets tried against the broken state before it is trusted |
| D-97 | A guard that fires mid-stream cannot set a status code, and the smoke test has to know that | Once the shell has started streaming, `redirect()` in a Server Component emits `<meta id="__next-page-redirect" http-equiv="refresh">` instead of a 307. Read the status alone and every refusal in the app looks like a page that rendered — which is what the first run of `smoke:roles` concluded, about all six roles at once, and it would have been reported as a catastrophic permission failure. The classifier reads the meta tag. The side effect worth knowing: a refused screen shows its shell for about a second before bouncing, because the page began rendering before the guard resolved |
| D-98 | Every screen is opened as every role, and the expected answer is read out of the screen's own guard | `permissions.ts` says who may open what, and a unit test that checked a page against that map would be asserting the map against itself. `npm run smoke:roles` takes the permission out of each page's own `requirePermission()` call, works out what the map says should happen, signs in as all six roles and finds out what does — thirty-six screens by six roles, which is more combinations than anybody checks by hand and where the interesting ones are always the boring ones nobody thought to try |
| D-99 | A page guard does not guard the action underneath it | A Server Action is a separate POST to a generated endpoint, reachable by anybody holding the action id whether or not they can open the page it came from. The page and the action are two doors into the same room. `tests/action-guards.test.ts` reads the body of every exported async function in a `"use server"` file and requires a check inside it, with two files exempt on purpose: signing in, and the public collection link where the token is the authorization (D-68) |
| D-100 | A skipped run is written down | Returning quietly left the console unable to tell "the cron fired at 7:15 and found the work already done" from "the cron never fired at all" — and which of those it is happens to be the only question the console exists to answer. The skip row carries no summary, because the status badge already says "Already done" in the reader's own language; the card shows the numbers from the last run that actually did something, which is a different row whenever the last attempt was a skip |
| D-101 | Nothing is outstanding on a day the school was shut | The daily summary subtracted submitted registers from the number of classes, so every Sunday reported nineteen registers outstanding — nineteen teachers apparently having failed to take one, on a day nobody was there. Found by running the job for a Sunday rather than by reading it |
