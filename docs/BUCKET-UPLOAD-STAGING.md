# Unfinished private bucket document uploads

The browser uploads to one private bucket object. A row remains `uploading` until the server verifies the file, or `failed` if verification fails. Such rows are not listed by the app; their metadata remains visible to people already scoped to that student under the existing database policy. An interrupted upload can leave a row and a private object, each object limited by the bucket's 10 MiB setting. There is no automatic cleanup or total storage bound.

The upload endpoint stops issuing capabilities and refuses finalization one hour after the row was created. Supabase signed upload capabilities expire after two hours. An operator can therefore identify candidates at least four hours after creation, allowing extra time for in-flight requests. Use a single operator, verify the target project, and select only rows created by this bucket upload flow (`storage_provider = supabase`, `client_request_id = id`, `upload_state` is `uploading` or `failed`), never `stored` or an existing document. Recheck each row's state and age before acting. Remove the matching private object first, then remove its still-unfinished row; if the object removal fails, retain the row for investigation. Do not run concurrent cleanup workers. This is a manual operational disposition, not a scheduled deletion job; any cleanup requires the appropriate separate authorization.

These timing rules apply only after the one-hour guard is deployed. Rows created by a version that could renew capabilities indefinitely cannot safely be cleaned based on creation time alone: first stop that version from issuing capabilities and wait at least two hours plus a conservative margin. A token issued before a stored document is deleted could recreate an unindexed private object until it expires; orphan inspection must account for this and must not delete stored objects.
